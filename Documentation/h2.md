# H2 embebida (`AUTO_SERVER`) — reemplazo de SQL Server/Docker

Este documento explica cómo quedó armada la base de datos real de este proyecto, tercer
motor que usa (Derby embebida → SQL Server en Docker → **H2 embebida**, aquí). El objetivo
del cambio: quitar la dependencia de Docker (`Documentation/sqlserver.md`, ahora histórico)
sin perder la posibilidad de conectarte tú mismo a la base con un cliente (IntelliJ,
DBeaver, etc.) al mismo tiempo que GlassFish la tiene abierta.

**Requisito previo**: este proyecto se despliega en **GlassFish 8** (JDK 21) — GlassFish 7
ya no existe en esta máquina (se desinstaló). Todo lo de abajo asume que ya estás parado
sobre GF8.

---

## 1. Por qué H2, y por qué `AUTO_SERVER=TRUE`

H2 es una base de datos escrita en Java, 100% embebible — no necesita un proceso de
servidor aparte ni un contenedor. La forma más simple de usarla (`jdbc:h2:/ruta/archivo`)
abre el archivo en modo **exclusivo**: si GlassFish ya lo tiene abierto, ningún otro
programa (IntelliJ, por ejemplo) puede conectarse al mismo tiempo.

`AUTO_SERVER=TRUE` resuelve justo eso: la primera conexión (la de GlassFish) arranca el
motor embebido normal, pero además **levanta un endpoint TCP en segundo plano** — cualquier
otra conexión posterior a la misma URL (con el mismo flag) se conecta a ese endpoint en vez
de pelear por el archivo. No hay que arrancar ni apagar nada a mano, a diferencia de Derby
(`start-database`) o SQL Server (`docker compose up`) — el server "aparece" solo con la
primera conexión real, y se apaga solo cuando la última conexión se cierra.

## 2. El pool en GlassFish

```bash
export AS_JAVA=/usr/lib/jvm/java-21-openjdk
ASADMIN=.../glassfish8/glassfish/bin/asadmin
DBPATH=.../glassfish8/glassfish/domains/domain1/databases/hellojakartadb

$ASADMIN create-jdbc-connection-pool \
  --datasourceclassname org.h2.jdbcx.JdbcDataSource \
  --restype javax.sql.DataSource \
  --property "url=jdbc\:h2\:${DBPATH}\;AUTO_SERVER\=TRUE:user=sa:password=sa" \
  H2Pool

$ASADMIN ping-connection-pool H2Pool
$ASADMIN set resources.jdbc-resource.jdbc/__default.pool-name=H2Pool
```

- El archivo vive en `domain1/databases/hellojakartadb.mv.db` — mismo espíritu que donde
  vivía la base de Derby, pero ahora en su propia carpeta (`databases/`, no
  `lib/databases/ejbtimer` que es del EJB timer interno de GlassFish, otra cosa).
  `user=sa`/`password=sa` son credenciales locales sin ningún significado especial — H2 las
  usa solo para separar "quién es el dueño del archivo", no hay nada que proteger en una
  base de desarrollo local.
- **`SQLServerPool` (el anterior) se dejó intacto, sin borrar** — sigue existiendo, ya no lo
  apunta nadie. Volver a él es un solo comando:
  `asadmin set resources.jdbc-resource.jdbc/__default.pool-name=SQLServerPool` + volver
  `eclipselink.target-database` a `SQLServer` en `persistence.xml` + redeploy (y volver a
  levantar el contenedor de Docker, claro).

## 3. El driver JDBC — y el bug real que obligó a usar una versión vieja

Igual que con SQL Server (`sqlserver.md` sección 3), el driver de H2 tiene que vivir en
`domain1/lib/` (el classpath compartido del servidor), no en el `.war`:

```bash
curl -sL -o "$GLASSFISH8/domains/domain1/lib/h2-1.4.200.jar" \
  https://repo1.maven.org/maven2/com/h2database/h2/1.4.200/h2-1.4.200.jar
```

**¿Por qué `1.4.200` y no la versión estable actual (`2.4.x`)?** Se probó primero con
`2.4.240` (la última) y falló al desplegar:

```
Internal Exception: org.h2.jdbc.JdbcSQLSyntaxErrorException:
Syntax error in SQL statement "CREATE TABLE SESION_CAJA (ID BIGINT [*]IDENTITY NOT NULL, ...)"
expected "..., GENERATED, ..."
```

**Causa real**: EclipseLink 5.0.1 (el que trae este GlassFish 8) genera, para columnas
`@GeneratedValue(strategy = GenerationType.IDENTITY)`, el SQL `BIGINT IDENTITY NOT NULL`.
H2 hasta la serie 1.4.x aceptaba esa forma corta; H2 2.x reescribió su parser SQL para ser
más estricto/estándar y ahora exige `BIGINT GENERATED BY DEFAULT AS IDENTITY NOT NULL` —
EclipseLink 5.0.1 todavía no genera esa forma nueva. Es una incompatibilidad real entre esas
dos versiones específicas, no un error de configuración.

**Quién se ve afectado**: solo las entidades con `GenerationType.IDENTITY`
(`SesionCaja`, `Usuario`). Las que usan `GenerationType.SEQUENCE` (`Producto`, `Factura`,
`FacturaDetalle` — ver incidente #15 de `bitacora-fixes.md`) generan `CREATE SEQUENCE ...`,
sintaxis que **sí** es idéntica entre H2 1.4 y 2.x, y nunca tuvieron problema en ninguna de
las dos versiones probadas.

**Fix**: usar `h2-1.4.200.jar` en vez de `2.4.240` — versión estable, muy usada en su
momento (fue el H2 default de Spring Boot durante años), y su parser sí acepta la sintaxis
`BIGINT IDENTITY` que genera EclipseLink. Verificado con `curl` real: `POST` a
`/sesiones-caja` (`IDENTITY`) y a `/productos` (`SEQUENCE`) funcionando ambos.

Después de cambiar el `.jar`, hace falta reiniciar el dominio para que lo tome:

```bash
$ASADMIN restart-domain domain1
```

## 4. Cómo te conectas tú mismo (IntelliJ)

1. Panel **Database**: `View → Tool Windows → Database`.
2. `+` → **Data Source → H2**.
3. En **General**, en vez de llenar host/puerto por separado, pon la URL completa (modo
   `AUTO_SERVER` se especifica ahí, no como campo aparte):

   ```
   jdbc:h2:/home/robute/Documentos/codes/SanboxTEST/glassfish8/glassfish/domains/domain1/databases/hellojakartadb;AUTO_SERVER=TRUE
   ```

   - User: `sa`
   - Password: `sa`
4. Si pide descargar el driver, dale a "Download driver files" (driver propio de IntelliJ,
   no tiene relación con el `.jar` que está en `domain1/lib/`).
5. `Test Connection` — **importante**: para que funcione, GlassFish tiene que estar
   corriendo (o al menos haber abierto la base una vez) — el `AUTO_SERVER` solo existe
   mientras haya al menos una conexión activa. Si GlassFish está apagado y eres la primera
   conexión, igual funciona (tú te conviertes en el "servidor" temporal), pero si luego
   arranca GlassFish necesitando el archivo, puede chocar si tu conexión sigue abierta en
   modo exclusivo — en la práctica, más simple: arranca GlassFish primero, conéctate tú
   después.
6. `Apply`/`OK`. Verás `HELLOJAKARTADB` (o el nombre por default `PUBLIC`) → `Tables` →
   `PRODUCTO`, `FACTURA`, `FACTURA_DETALLE`, `SESION_CAJA`, `USUARIO`.

## 5. El único cambio de código real: `persistence.xml`

```xml
<property name="eclipselink.target-database" value="org.eclipse.persistence.platform.database.H2Platform"/>
```

**Ojo**: a diferencia de `SQLServer`/`Derby` (que sí son alias cortos reconocidos), `H2`
solo no funciona — hace falta el **nombre completo de la clase**
(`org.eclipse.persistence.platform.database.H2Platform`), si no falla el deploy con
`Database platform class [H2] not found`. Fue el primer error que salió al hacer este
cambio, antes de llegar al bug real de la sección 3.

## 6. Verificado funcionando de punta a punta

Con `mvn package` (JDK 21) + `asadmin deploy --force=true`, contra `h2-1.4.200.jar`:

- **`GET /api/productos`** → EclipseLink creó las 5 tablas solo, `DatosIniciales` sembró
  los 3 productos de siempre.
- **`POST /api/productos`** (`SEQUENCE`) → id nuevo, consecutivo, sin `flush()` manual.
- **`POST /api/sesiones-caja`** (`IDENTITY`) → antes fallaba con `2.4.240` (tabla ni
  siquiera se creaba), funciona con `1.4.200`.
- **`POST /api/facturas`** con relación a `Producto` (precio recalculado en servidor) → OK.
- **`DELETE /api/productos/{id}`** con conflicto de FK → `409` limpio (vía
  `EJBExceptionMapper`, incidente #14), sin exponer detalle interno.

## 7. Reproducir esto desde cero

1. Descargar `h2-1.4.200.jar` (sección 3) a `domain1/lib/`.
2. Crear el pool + repuntar `jdbc/__default` (sección 2).
3. `asadmin restart-domain domain1` (con `AS_JAVA` en JDK 21).
4. Confirmar que `persistence.xml` diga
   `eclipselink.target-database=org.eclipse.persistence.platform.database.H2Platform` (ya
   commiteado, no hace falta tocarlo de nuevo).
5. `mvn package` (JDK 21) + `asadmin deploy --force=true` del WAR.
